วันที่ 3 พฤศจิกายน 2569 • รอบปรับหน้าตาตามภาพอ้างอิง 5 หน้า • เป้าหมายภายใน 2 วัน

## คำสั่งและขอบเขตที่เจ้าของยืนยัน

เจ้าของกล่าวว่า “อยากได้แบบนี้เลย” และ “งั้นเอาแบบนี้เลย” หมายถึงให้ใช้ภาพ Home, Visit, Meditation, Q&A และ Centers ที่แนบเป็นแบบหลักด้านหน้าตา ไม่ใช่เพียงหยิบสีมาใช้ แล้วออกแบบองค์ประกอบใหม่จนต่างจากภาพ

- ZIP ไม่มี `.git`, `.env`, `node_modules`, `dist` ไม่ใช่หลักฐานว่าเป็น checkout ที่พร้อม push หากจะใช้ Git ให้ clone repo แยก สร้างสาขา `design/reference-20261103` แล้วเทียบ/นำ source ชุดนี้เข้า โดยรักษา `.git` ของ checkout ใหม่ไว้ ห้าม reset หรือ clean โฟลเดอร์เดิม

- งานรวมนี้ยังไม่ commit/push บน GitHub อย่าดึง main แล้วถือว่ามีงานทั้งหมดจาก ZIP แล้ว

## 2. เป้าหมายหน้าตาที่ต้องตามภาพ

แนวภาพ: สงบ อบอุ่น อยุธยา พื้นครีม หัวเรื่องแดงเข้ม ปุ่มอิฐมอญแดง เส้น/ไอคอนทองบาง ๆ ใช้ภาพพระและโบราณสถานเป็นจุดนำสายตา การ์ดสีอ่อนมีเงานุ่มและเส้นขอบ ไม่ใช้บล็อกเขียวเข้มเป็นสีหลักต่อจากหน้าเดิม

ค่าเริ่มต้นเพื่อเทียบภาพ: พื้น `#FFF8EE`, ผิวการ์ด `#FFFDF7`, หัวเรื่อง `#681B16`, ปุ่ม `#A43D1D`, ทอง `#B77A24`, ข้อความ `#30251E` ปรับได้เมื่อเทียบจริงให้คอนทราสต์อ่านชัด

- ส่วนหัวใช้โลโก้ที่มีอยู่ เมนู 5 หน้า และตัวเลือก TH/EN; มือถือใช้เมนูเปิดปิดได้ตามภาพ พร้อมสถานะ active, focus, aria-expanded และปิดด้วย Escape
- หัวเรื่องอังกฤษใช้ serif ที่อ่านชัด ภาษาไทยใช้ฟอนต์ที่รองรับไทยจริงและน้ำหนักสัมพันธ์กัน เนื้อหา 16px เป็นค่าเริ่มต้น ไม่ย่อข้อความเพื่อยัดให้เท่าภาพ
- Hero เป็นภาพกว้าง มีพื้นที่ว่างสำหรับข้อความและไล่เฉดอ่อนรองรับตัวอักษร เก็บลำดับ/สัดส่วนให้ใกล้ภาพโดยไม่ทำตัวอักษรจมหายกับฉาก
- เวลา/สถานที่อยู่แถบสรุปใต้ภาพเปิดหน้า ปุ่มหลักเด่นหนึ่งระดับ ปุ่มรองเป็นเส้นขอบ
- ลายวัด/ลายน้ำใช้พอเป็นบรรยากาศ รักษาลายนั่งสมาธิเดิมหากใช้ ไม่ให้ลายแย่งเนื้อหา
- ไม่ใช้ภาพ mockup ทั้งหน้ามาวางเป็นหน้าเว็บ ข้อความ ปุ่ม แผนที่ และเครื่องเล่นต้องเป็นองค์ประกอบที่ใช้งานจริง

## 4. จุดที่ต้องปรับจากภาพให้ตรงข้อเท็จจริง

1. การ์ดสาธารณะใช้ชื่อ “ถาม MonkChat” / “Ask MonkChat” ไม่ใช้ “Ask MonkChat AI” หรืออ้างว่า trained by monks เพราะคำตอบมาจากคลังที่ตรวจแล้ว AI ช่วยร่างสำหรับพระนิสิตยังอยู่ `/admin/assistant` หลังล็อกอิน
2. ไม่แสดงชื่อผู้ตรวจ แหล่งอ้างอิง หรือป้ายสถานะการตรวจแก่ผู้มาเยือน ระบบหลังบ้านเก็บเหมือนเดิม ไม่พบคำตอบให้บอกตรง ๆ
3. ภาพ Home และ Visit ระบุคนละสถานที่ ห้ามคัดทั้งคู่เป็นข้อมูลจริง ใช้ข้อมูลโครงการที่ยืนยันแล้วชุดเดียว หากยังขัดกันให้คงข้อมูลเดิมและบันทึกจุดรอยืนยัน
4. เสียงที่ตรวจจริงยาวประมาณ 5:26 แต่ metadata และ VTT จบ 5:00 ใช้ duration จาก media เมื่อพร้อม ไม่เขียนทับเป็น 5:00 ตามภาพ ไม่ยืด/ตัดเสียงหรือย้าย subtitle อัตโนมัติ ต้องแยกการฟังตรวจเป็นงานค้าง
5. ปุ่ม Save/Share, ค้นหา, ตัวกรอง และแผนที่ต้องทำงานจริง หากข้อมูล/ความสามารถยังไม่รองรับ ให้ใช้ทางเลือกที่ทำงานได้หรือเว้นออกพร้อมแจ้ง ไม่ใส่ปุ่มหลอก
6. ภาพอ้างอิงเป็นแบบการออกแบบ ไม่ใช่หลักฐานกิจกรรม/สถานที่จริง ใช้สื่อเดิมที่โครงการมีสิทธิ์หรือภาพที่ยืนยันสิทธิ์แล้ว ภาพประกอบสร้างใหม่ห้ามใช้แทนหลักฐานกิจกรรมจริง

## 5. แผนภาพประกอบ

ตรวจรูปที่มีใน `public/images/home/` ก่อน เริ่มจากรูปเดิมและเลือก crop ให้ใกล้แบบ บันทึกชื่อรูป/ตำแหน่งโฟกัสแยก desktop กับ mobile ไม่ดึงคนพระออกนอกจอบนมือถือ

หากไม่มี hero ที่ใกล้แบบ ให้รายงานช่องว่างและขอ asset ที่เจาะจง เช่น hero กว้างมีพื้นที่ข้อความกลางซ้าย พร้อมสัดส่วนที่ต้องการ ใช้รูปเดิมเป็นชั่วคราวแล้วทำโครงต่อ อย่าติดรอภาพจนหยุดทั้งงาน อย่าเปลี่ยนโทน/ผังใหม่เพื่อหลีกเลี่ยงงานเตรียมภาพ

## 6. การจัดหน้าจริง

- Desktop: กว้างเนื้อหาประมาณ 1120–1200px; คงจังหวะ hero → แถบสรุป → เนื้อหาแบบภาพ
- Tablet: เปลี่ยนเป็น 2 คอลัมน์เท่าที่อ่านสบาย; FAQ กับการ์ดแชทเรียงลงได้
- Mobile: hero crop ตามจุดสนใจ, ปุ่มหลักกว้างพอ, แถบกิจกรรม 2×2, การ์ดหนึ่งคอลัมน์/แบบภาพซ้ายข้อความขวา, ขั้นตอนฝึกพับได้, เนื้อหาไม่ล้นแนวนอน
- กดได้อย่างน้อยประมาณ 44×44px; เมนูและ accordion ใช้ keyboard ได้ มี focus ชัด และชื่อปุ่มสำหรับ screen reader
- ภาษาไทยเป็นค่าเริ่มต้น ภาษาอังกฤษใช้ทดสอบอีกชุด รูป mockup เป็นอังกฤษไม่ได้เปลี่ยน default ของโครงการ
- การ์ดแชทมุมล่างต้องไม่บัง player, CTA หรือเนื้อหามือถือ; หน้า Q&A หากมีการ์ดแชทในเนื้อหาต้องไม่เปิด widget ซ้ำสองตัว

## 7. ลำดับภายใน 2 วัน

วันแรก: ตรวจฐาน/ทำสำเนา → สี/ฟอนต์/Layout/ภาพ → Home และ Meditation → บันทึกภาพจอจริงให้เจ้าของเห็นเร็ว แล้วใช้ระบบเดียวกันกับอีก 3 หน้าในขอบเขตที่อนุมัติ

วันที่สอง: เก็บทั้ง 5 หน้า → responsive/TH-EN/สถานะโหลด-ว่าง-ผิดพลาด → ตรวจ flow และ tests → ส่งชุดตรวจรับ

ทำต่อในขอบเขตนี้ได้โดยไม่ถามอนุมัติรายละเอียดเล็กซ้ำ ถ้าต้องเปลี่ยนขอบเขต/ข้อมูลหลักให้ถามเฉพาะจุดนั้น งานที่ไม่ขึ้นต่อกันให้ทำต่อได้ หากครบเวลาแล้วยังไม่ผ่านต้องรายงานสิ่งค้างตรง ๆ ไม่อ้างว่าพร้อมจาก build อย่างเดียว

## 8. สิ่งที่ต้องรักษาและไม่รวมในรอบนี้

- งบ 0 บาท ไม่เพิ่ม paid API/แพ็กเกจ/overage และไม่เพิ่ม dependency ที่ไม่จำเป็น
- ไม่เปลี่ยน schema, RLS, auth, role checks, private AI endpoint หรือ migration โดยอาศัยงานปรับ UI
- ห้ามรัน `update_track.sql`, `update_track2.sql` หรือ migration ใดกับฐานข้อมูลจริงในรอบนี้
- คง migration Q&A ฉบับเดียว `20261025130443_lock_verified_qa_content.sql`; ยังต้องผ่าน disposable Supabase/gateway ก่อนพิจารณาใช้งานจริง
- ไม่ตัดงาน merged จาก Windows หรือแก้ทับโฟลเดอร์เดิม ไม่ commit/push/merge/deploy จนกว่าจะมีคำสั่งเจ้าของให้ทำขั้นนั้น บรีฟนี้อนุมัติการแก้และทดสอบในเครื่อง
- ไม่ส่งรหัสผ่าน `.env*` (ยกเว้น `.env.example`), token, `.git`, `node_modules`, `dist`, `supabase/.temp` ในไฟล์ส่งกลับ

## 9. หลักฐานก่อนส่งกลับ

1. รัน `npm test`, `npm run lint`, `npm run build` (รวม TypeScript) และ `git diff --check` เมื่อมี Git; บันทึกผลจริงพร้อมจำนวน tests หลังเปลี่ยน ไม่คัดผลเดิม 64 tests มาอ้าง
2. ตรวจทุกหน้าอย่างน้อยที่ 360, 390, 768, 1024, 1440px ทั้ง TH/EN: ไม่มีล้นแนวนอน ข้อความอ่านออก ปุ่มทำงาน บันทึก screenshot อย่างน้อย 390/768/1440px ของทั้ง 5 หน้า รวม 15 ภาพ พร้อมตารางผล TH/EN
3. ตรวจ QR route `/visit`, สลับภาษา, เมนูมือถือ, accordion, FAQ ค้นหา/ไม่พบ, player เล่น-หยุด-เลื่อน, captions/transcript และลิงก์ map/resources
4. Smoke test login/ออกจากระบบและขอบเขต Public/Team/Owner ที่ทำได้ ถ้าไม่มีบัญชีหรือเครื่องมือให้ระบุว่าไม่ได้ตรวจ ห้ามสร้างบัญชี/เปลี่ยน role เอง
5. เทียบ screenshot จริงคู่กับภาพอ้างอิง รายงานสิ่งที่ยังต่าง รวมภาพประกอบที่ยังแทนชั่วคราว
6. อัปเดต `HANDOFF.md` และเขียน `docs/ANTI_REVIEW_REPORT.md`: ฐานงาน, ไฟล์ที่แก้, package ที่เปลี่ยน, ผล checks/viewport, ปัญหาค้าง, branch/commit ถ้ามี และสิ่งที่ต้องทำต่อ
7. ส่ง source ZIP ใหม่ที่ตัดสิ่งต้องห้ามข้างต้น พร้อม report และ screenshots ถ้ามี Git ส่ง diff patch เพิ่มได้ ต้องรวมไฟล์ใหม่ที่ยัง untracked ด้วย ไม่ส่งเฉพาะ `git diff` จนไฟล์ใหม่หาย

## 10. การประสานงาน
